El punto de partida

¿Por qué no alcanza con pedirle código a la IA?

Cuando le pedís a un IDE con IA que "haga una app de gestión de autos", el modelo no sabe qué querés realmente. Adivina. Y lo que genera es genérico, incompleto o no escala.

🎲
El modelo adivina
Sin contexto claro, el ejecutor toma decisiones de diseño que vos no pediste. Puede estar bien o puede estar todo mal.
🔄
Cambios constantes
Sin un plan previo, cada consulta nueva rompe lo que ya estaba. El sistema nunca converge hacia algo sólido.
🏗️
Sobre-ingeniería desde el día 1
Quieren construir todo de entrada. Resultado: ni el MVP queda bien y el proyecto se abandona.
⚠️
El error más común

Muchos equipos junior empiezan a escribir código (o pedirle al IDE que lo haga) antes de entender qué problema están resolviendo y qué límites tiene el sistema. El resultado: reescribir todo desde cero a las dos semanas.

"El problema no es que la IA sea mala escribiendo código. El problema es que vos le estás pidiendo que haga el trabajo de tres personas a la vez: analista, arquitecto y desarrollador."

El modelo mental

El roadmap: de la idea al código

Antes de escribir una sola línea de código, necesitás recorrer cuatro etapas. Cada una tiene un propósito claro y prepara el terreno para la siguiente.

💡
Idea
¿Qué problema concreto querés resolver?
🌐
Visión
¿Cómo se ve el sistema completo en el futuro?
⚙️
Core
¿Cuál es el modelo de datos y entidades centrales?
🚀
MVP
¿Qué es lo mínimo que aporta valor real?

La idea es la semilla. No es un listado de funcionalidades, es una frase que describe el dolor que el sistema va a resolver. Tiene que ser tan clara que cualquier persona pueda entenderla.


Ejemplo: "Necesito saber qué autos tiene la agencia, de dónde vienen y a cuánto se venden, porque ahora lo tenemos en papel y nos perdemos stock."


Nótese: menciona el problema actual (papel), el dato que falta (origen, precio) y el impacto (se pierde stock). Una buena idea tiene esos tres elementos.

La visión describe a dónde querés llegar en el largo plazo. No es lo que vas a construir hoy. Es la foto del sistema completo cuando esté maduro. Sirve para que todas las decisiones técnicas de hoy apunten en la misma dirección.


Ejemplo (agencia de autos):

  • Sistema web de gestión de inventario de autos
  • CRM para registrar clientes y oportunidades de venta
  • Panel de seguimiento de ventas y comisiones
  • Historial de cada unidad (service, propietarios anteriores)
  • Integración con portales de publicación (ML, etc.)

El core son las entidades centrales del sistema: los datos que no pueden faltar porque todo lo demás depende de ellos. Definir el core bien es la decisión de diseño más importante que vas a tomar.


Ejemplo (agencia de autos):

Auto {
  id, marca, modelo, año,
  origen (nacional/importado),
  precio_lista, precio_venta,
  estado (disponible/vendido/reservado),
  fecha_ingreso
}

Todo lo demás (clientes, ventas, historial) viene después. El core es la base.

MVP significa Minimum Viable Product. No es "lo más simple que puedo hacer". Es "lo mínimo que resuelve el problema original de forma completa". La diferencia es importante.


¿Entra en el MVP?¿Por qué?
CRUD completo de autosSin esto no hay sistemaSí
Listado con filtros básicosNecesario para encontrar un autoSí
Estado del auto (disp/vendido)Información mínima esencialSí
CRM de clientesVisión, no MVPNo
Publicación en MercadoLibreIntegración compleja, no urgenteNo
Dashboard de ventasNo hay ventas aún que mostrarNo
✅
Regla de oro del MVP

Si podés usar el sistema para resolver el problema original sin esa funcionalidad, no va en el MVP.

El modelo de trabajo

Los dos roles: arquitecto y ejecutor

La clave del flujo está en separar responsabilidades. En un equipo real, el arquitecto y el desarrollador tienen roles distintos. Con IA, hacemos lo mismo.

🧠 Arquitecto
GPT-4 / Claude (en chat)
Piensa
  • Define la visión completa del sistema
  • Establece el modelo de datos y entidades
  • Decide el alcance exacto del MVP
  • Define las tecnologías y estructura del proyecto
  • Genera el plan de acción para el ejecutor
  • Pone las reglas y restricciones
  • No escribe código
⚡ Ejecutor
Antigravity / Cursor (IDE con IA)
Ejecuta
  • Recibe el plan del arquitecto
  • Lo lee completo antes de hacer nada
  • Devuelve su entendimiento del plan
  • Lista archivos que va a crear
  • Propone orden de implementación
  • Espera confirmación antes de ejecutar
  • No toma decisiones de diseño
  • Si algo no está claro, consulta al arquitecto

¿Por qué este flujo?

El ejecutor (el IDE) es muy bueno escribiendo código, pero toma malas decisiones de arquitectura sin contexto. El arquitecto (GPT en modo razonamiento) es muy bueno pensando estructuras, pero está lejos del código. Al combinarlos correctamente, obtenés lo mejor de cada uno.

Caso de estudio

Sistema para agencia de autos — paso a paso

Vamos a aplicar todo el roadmap a un caso real. Seguí cada paso y entendé qué decisión se toma en cada etapa y por qué.

Modelo de datos — diagrama de entidades

Así se ve el core del sistema. En el MVP solo necesitamos la tabla Auto. Las demás entidades se agregan en versiones futuras (visión).

¿Qué construimos en cada etapa?
MVP — CRUD de autos100% del alcance v1
v2 — Clientes + OportunidadesAgrega el CRM básico
v3 — Ventas + HistorialCierra el ciclo de negocio
v4 — Integraciones externasMercadoLibre, reportes, API

Recorrido paso a paso del caso

1
Identificar la idea
La agencia tiene su stock en papel. Pierde unidades, no sabe precios actualizados, no conoce el origen de cada auto. El problema está claro: falta de visibilidad del inventario.
2
Definir la visión con el arquitecto (GPT)
Le pasamos la idea al arquitecto con el prompt correcto. GPT devuelve la visión completa: sistema web, CRM, módulo de ventas, historial de unidades, integraciones futuras.
3
El arquitecto define el core
Del análisis del sistema, el arquitecto extrae las entidades principales: Auto, Cliente, Venta, Historial. Define atributos, tipos de dato, relaciones y restricciones.
4
El arquitecto delimita el MVP
Decide qué entra y qué no. MVP = CRUD de autos + listado con filtros + estados. Justifica cada decisión. Esto es lo que le pasamos al ejecutor.
5
El arquitecto genera el plan de acción
El plan incluye: tecnologías, estructura de carpetas, archivos a crear, orden de implementación, reglas de código. Es el documento que recibe Antigravity.
6
El ejecutor lee el plan y confirma
Antigravity recibe el plan, lo lee completo y devuelve: entendimiento del alcance, lista de archivos a crear, orden de implementación y dudas. Vos lo revisás y confirmás.
7
El ejecutor construye el sistema
Una vez confirmado, Antigravity ejecuta el plan siguiendo las reglas estrictamente. Si encuentra algo que no estaba en el plan, consulta antes de decidir solo.
Prompts completos

Los prompts que vas a usar

Estos son los prompts listos para copiar y usar. El primero va a GPT (el arquitecto). El segundo va a Antenagravity (el ejecutor), pegando el output del primero.

Prompt 1 — El arquitecto (GPT)

Pegá esto en ChatGPT o en cualquier LLM de razonamiento potente. Ajustá el bloque de contexto con tu propio caso.

prompt · arquitecto 
## ROL
Actuá como arquitecto de software senior y analista de sistemas.
Tu trabajo es pensar y planificar. No generas código.

## CONTEXTO DEL SISTEMA
Estoy desarrollando un sistema para una agencia de venta de autos.
Necesitan gestionar su inventario: qué autos tienen, de dónde
vienen (origen/procedencia) y el precio de venta.
Actualmente lo hacen en papel y pierden control del stock.

## TU TAREA — realizá estos pasos en orden:

1. VISIÓN DEL SISTEMA
   Define cómo se vería el sistema completo y maduro.
   Incluí módulos, funcionalidades principales y usuarios del sistema.

2. CORE DEL SISTEMA
   Identificá las entidades principales (modelo de datos).
   Para cada entidad: nombre, atributos clave y tipo de dato básico.
   Indicá las relaciones entre entidades.

3. ALCANCE DEL MVP
   Define exactamente qué entra y qué NO entra en el MVP.
   Justificá cada decisión con una razón concreta.
   El MVP debe resolver el problema original de forma completa.

4. PLAN DE ACCIÓN PARA EL EJECUTOR
   Generá un plan estructurado que incluya:
   - Stack tecnológico recomendado (con justificación)
   - Estructura de carpetas del proyecto
   - Lista de archivos a crear
   - Orden de implementación (paso a paso)
   - Reglas y restricciones de código que el ejecutor debe seguir

## RESTRICCIONES
- No generes código bajo ningún concepto
- El plan debe ser ejecutable por otro modelo sin ambigüedad
- Usá formato estructurado con secciones y numeración clara
- Sé específico: nada de "etc." o respuestas genéricas

Por qué pedimos el entendimiento primero

Si el ejecutor entendió mal el plan y arranca a codear directamente, vas a tener que rehacer todo. Pidiéndole que devuelva su entendimiento primero, podés corregir antes de que sea tarde. Es el mismo principio que un desarrollador que repite el brief antes de arrancar.

Práctica en clase

Tu turno — aplicá el flujo

Ahora replicás el flujo con tu propio proyecto (o el de la agencia si no tenés uno). Seguí estos pasos en orden.

📝
Paso 1 — Escribí la idea
5 minutos

En una sola frase o párrafo corto: ¿qué problema resuelve tu sistema? ¿Quién lo usa? ¿Qué duele hoy sin él? Sin mencionar tecnología todavía.

🧠
Paso 2 — El arquitecto
15-20 minutos

Pegá el Prompt 1 en GPT con tu contexto. Leé el output completo. Chequeá que el MVP esté bien delimitado y que el modelo de datos tenga sentido para tu caso.

🔍
Paso 3 — Revisá el plan
10 minutos

Antes de pasarle el plan al ejecutor, preguntate: ¿el MVP resuelve el problema original? ¿Las entidades tienen sentido? ¿Hay algo que sobre o falte? Pedile ajustes al arquitecto si hace falta.

⚡
Paso 4 — El ejecutor
20-30 minutos

Pegá el Prompt 2 en Antigravity con el plan de GPT. Leé el entendimiento que devuelve. ¿Entendió bien? ¿La lista de archivos tiene sentido? Confirmá solo si todo está claro.

⚠️
Errores comunes en la práctica

No saltees pasos. Si vas directo al ejecutor sin haber pasado por el arquitecto, vas a tener los mismos problemas de siempre. El valor está en el proceso completo, no en los prompts sueltos.

💡
Tip para iterar con el arquitecto

Si el output de GPT no te convence, no lo descartés: preguntale. "¿Por qué pusiste X en el MVP y no Y?", "¿Qué pasaría si agrego Z desde el principio?". El arquitecto puede justificar y ajustar sus decisiones.

Validación final

Checklist de cierre

Glosario y conceptos clave

Una referencia rápida para consultar cuando tengas dudas durante el desarrollo.

Minimum Viable Product. El subconjunto mínimo de funcionalidades que resuelve completamente el problema original y aporta valor real a los usuarios. No es un prototipo incompleto: es una versión funcional y completa de la solución más simple posible.

Las entidades y relaciones centrales del modelo de datos. Son los datos sin los cuales el sistema no puede funcionar. En la agencia de autos, el core es el Auto con sus atributos básicos. Todo lo demás se construye sobre este core.

El rol responsable de definir la estructura de alto nivel de un sistema: qué componentes lo forman, cómo se comunican, qué tecnologías se usan y por qué. En este flujo, usamos un LLM (GPT) en ese rol para que piense el sistema antes de que nadie escriba código.

Porque los modelos de lenguaje pueden interpretar de forma diferente a lo que uno espera. Pidiéndole que reformule el plan con sus palabras y liste lo que va a hacer, podés detectar malentendidos antes de que se conviertan en código equivocado. Es el equivalente a un desarrollador que repite el brief antes de arrancar.

Es normal. El plan del arquitecto es un punto de partida, no una biblia. Si al revisar el output de GPT ves algo que no tiene sentido, le preguntás, le pedís que lo justifique o que lo ajuste. El arquitecto puede iterar. Lo importante es que los ajustes se hacen en el plan, no en el código.

En decisiones técnicas de implementación que no afecten la arquitectura (por ejemplo: cómo nombrar una variable interna, qué método de utilidad usar). Si hay algo que afecte la estructura, los archivos, las entidades o el scope: siempre consulta antes.
